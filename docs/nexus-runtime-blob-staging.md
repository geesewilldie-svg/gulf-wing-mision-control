# Explicit local Ollama blob staging

After an archive review and an observed sufficient Ollama storage snapshot, Nexus offers **Stage weights in Ollama** with source/license confirmation. This is the first runtime write slice. It copies or acknowledges a content-addressed binary blob; it does not create a model manifest, choose a model, generate an answer or activate inference. Opening/reloading any review does not stage weights.

The controller-only, same-origin action accepts exactly `stage-runtime-blob`, fixed archive slot, inspected source receipt digest, expected recorded license, `licenseReviewed: true` and `stageOnly: true`. Caller paths, URLs, model names, prompts and runtime options are rejected. The archive must be a recorded completed transfer, match its full current size/SHA-256 and receipt, and expose complete bounded GGUF metadata with a declared architecture. These checks do not validate tensor/runtime compatibility. The recorded license is bound by the source digest and reviewed by the operator; no fresh Hub terms request is made.

A fresh runtime-reported storage/path and free-space-buffer observation is required before any upload. It remains an observation rather than independent authentication of the runtime process or a space reservation. The action uses the same trusted loopback service boundary as existing local Ollama operations and does not enable model import simply because storage matches. Local answer/planning/diagnostic admission is shared for the operation; competing Nexus generations are rejected. Multiple server installations or unrelated Ollama clients are not coordinated.

The operation holds the source's read-only file handle inside the full-hash check's final identity fence. It sends HEAD to the fixed `http://127.0.0.1:11434/api/blobs/sha256:<source hash>` endpoint. A 200 response reuses reported existing presence. Only 404 permits one POST, streaming at most the exact source size in 64 KiB chunks with no credentials or redirects. Streamed size/SHA-256 must agree, the runtime must return 201, and a subsequent HEAD must return 200. The overall existing source operation has a ten-minute cooperative deadline and a 4 GiB source limit. Source/receipt identity is checked again before acceptance. No create, pull, delete, generation, custom Modelfile or native command is called.

This is runtime acknowledgment, not an independent hash readback of the runtime's stored copy. Existing presence can describe a blob originally stored by another operation. Original archive bytes, transfer receipt and modification time stay unchanged. A separately claimed `runtime-blob-stage.json` records source receipt/hash/size, run/time and started/staged/failed/cancelled/unconfirmed outcome. Initial creation is exclusive; only the owned open receipt is updated/read back. Prior, malformed or unsafe receipts are retained and block replay. A crash can leave incomplete metadata. Archive listing projects known receipt fields only and performs no runtime probe or retry.

Once POST is attempted, cancellation, early/failed acknowledgments, changed source or final receipt failure retain uncertainty rather than returning success. Closing the page can leave a blob or receipt. No automatic retry, cleanup/delete or overwrite of a prior receipt is supplied. The operator must inspect the retained outcome; explicit runtime-presence reconciliation/receipt recovery and model creation are later slices. A historical staged receipt is not a fresh presence check or permanent guarantee.

Official contract reviewed November 27, 2026: [Ollama blob HEAD/POST API](https://github.com/ollama/ollama/blob/main/docs/api.md#push-a-blob). Validation uses real disposable source/receipt files, synthetic responses and an owned HTTP runtime fixture which writes/rechecks tiny fixture blobs. It does not establish native Windows acceptance, actual Ollama storage integrity, model import compatibility or real model inference.

An explicit [current presence check](nexus-runtime-blob-check.md) is now available from retained archive history. It preserves staging outcomes and performs no upload/retry or receipt recovery; current reported presence remains distinct from independent runtime integrity and model creation.
