# Explicit single-frame local description

During an active **Connections → Camera and screen** preview, **Describe one frame locally** can inspect installed models and check a selected model's reported capabilities. Only an inspected model reporting both `vision` and `completion` enables **Ask about this frame locally**. Opening the section, starting preview, listing models or inspecting capabilities never submits an image for generation. No model is downloaded or selected as the saved default by this flow. The owner's existing text model may not support images.

The action samples one live visible video frame into an ephemeral canvas, reduces its longest edge to at most 960 pixels and prepares JPEG at quality 0.75, at most 512 KiB. Optional browser-added ICC/EXIF/comment headers are removed before transfer; the server independently rejects forbidden metadata in the complete submitted envelope. The canvas is cleared immediately after encoding. This is a separate explicit transfer from the browser to the paired Nexus server and its loopback Ollama service; on a phone, the frame leaves the phone for that server. It does not use a hosted provider, owner memory, file retrieval, prior frames or conversation history. Stopping preview unmounts analysis, aborts the pending request and discards its result; cancelled/late responses are not accepted. Nothing resumes automatically.

## API and resource contract

Controller-only, same-origin `POST /api/sync/vision` accepts action `analyze-local-frame`, inspected simple local model name/digest, source `camera` or `screen`, canonical client capture timestamp, base64 JPEG, `analyzeOnce: true` and an optional bounded `question`. Legacy seven-field callers use the default description question; see [visual questions](nexus-visual-questions.md). Body size is limited to 710,000 bytes; Image URLs, caller system prompts/options, histories and extra fields are rejected. The supplied capture timestamp must be within thirty seconds of the server clock on receipt. It is client-reported provenance, not independent proof of capture time or source; devices with substantial clock skew must correct their clocks.

Canonical base64, byte limits and the full JPEG marker envelope are checked before runtime requests. Only eight-bit baseline/progressive JPEG with one declared frame, one/three components, dimensions at most 960 × 960, bounded scans and final end marker is admitted. EXIF/ICC/comments, nonempty JFIF thumbnails, dynamic-height extensions, duplicate/unsupported frame declarations, oversized/trailing data and unsupported markers reject. These checks bound declared image input; they do not decode/sanitize entropy or independently authenticate camera content. Actual image decoding remains the runtime's responsibility.

The action shares local answer/planning/diagnostic admission. Fresh catalog/show/catalog metadata checks must establish the selected digest and vision/completion capabilities without remote-model reports. One fixed loopback `/api/generate` request contains that JPEG and an application-owned prompt envelope containing only the normalized current question, with no owner context. It requests 128 output tokens, a 1024-token context, zero temperature, nonstreaming/no-thinking output and immediate unload. A sixty-second request deadline includes metadata and generation. These are requested resource settings, not a measured RAM/GPU fit or an operating-system hard execution limit.

Only a complete, bounded text response from the same reported model can be accepted; known over-budget token reports, control characters, remote identity, changed catalog digest/default and incomplete/oversized responses reject. Raw thinking, context and unrelated fields are projected out. Cancellation, timeouts and uncertain responses never trigger a retry or hosted fallback; runtime work/unload may remain uncertain. The trusted loopback service boundary is unchanged rather than independently process-authenticated.

## Result lifetime and interpretation

A result identifies requested/reported model, reported manifest digest, source, client capture and server completion times, dimensions/bytes and elapsed time. The text is rendered as plain text, explicitly labelled an unverified description of one historical captured frame. It is not a live feed, verified fact, instruction, execution receipt or permission for any action. Image text is treated as untrusted input in the fixed prompt; the returned text has no execution path. The result is cleared on another request, model change, denial/stale response, preview stop, visibility loss or navigation.

Nexus adds no image/result persistence, knowledge indexing, diagnostic-history receipt, provider event, recording or automatic spoken/conversation ingestion. The browser/request/runtime necessarily hold transient image data for processing; the underlying runtime/OS may have its own operational behavior. Local-only means no hosted-provider adapter is called, not that the image remains on a phone or never enters the local runtime.

Contract reviewed November 27, 2026: [official Ollama Generate with images](https://github.com/ollama/ollama/blob/main/docs/api.md#request-with-images). Tests use actual browser-generated synthetic JPEGs and owned HTTP/runtime fixtures, not an actual model decoder or personal camera. Real vision-model quality/decoding, Windows/Android camera and capture chooser behavior, and the owner's laptop hardware fit remain unverified. Continuous vision, voice-driven visual questions, hosted image sharing, durable visual evidence and remote laptop capture are separate architecture work.
