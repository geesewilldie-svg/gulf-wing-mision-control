# Conversational laptop maintenance

In Auto or Local mode, type or say “Check laptop services” or “Start missing Nexus services”. These commands call the same adapter as Connections → Device access → Laptop maintenance. They require an authenticated paired controller, a Windows host and the existing local maintenance setting. They do not enable that setting or add permissions. Optional “Nexus” and “please” prefixes are accepted; compound commands and shell arguments are not interpreted as maintenance operations. Other questions continue through normal assistant routing without gaining execution tools.

The check runs the fixed connection diagnostic; start runs the existing launcher with `--no-browser`. No installation, updates, process termination, administrator commands, arbitrary PowerShell, file edits or browser automation are added. Cloud, Compare and Knowledge-only modes reject recognized maintenance requests before provider use. The Android client requests work on its paired Windows host, not on Android itself.

Responses show the operation reference and observed adapter outcome. A successful child exit means the operation returned successfully, not proof that every model, microphone or account is ready. Needs-attention/timeout does not establish readiness; inspect private laptop logs. Retrying start reuses the existing launcher's service checks; this is not a durable exactly-once broker. Closing or muting the browser after dispatch does not guarantee cancellation of the maintenance process. Pending conversational requests check cancellation before dispatch.

Private audit records retain action/reference/state/time without recording the conversation or child output. A local permission revocation during the initial audit write prevents dispatch. Native Windows execution, service availability and voice transcription need laptop acceptance; Linux tests use synthetic host conditions without starting Windows services.

## Durable operation receipts

New maintenance operations now record action, request ID, outcome and timestamps in the existing Foundation SQLite database. A transactional claim allows only one recorded running maintenance invocation across server processes sharing that database. This is not OS fencing of an arbitrary process. A repeated request ID with the same action returns its existing receipt; reusing that ID for a different action is rejected. Conversation submissions carry their generated request ID; an ordinary new user submission has a new ID and is a new request. Direct maintenance-panel submissions receive a fresh internal ID. This is request-ID deduplication, not sentence-level deduplication or an exactly-once guarantee for effects.

Ask “Show laptop operations” to retrieve the latest ten receipts, including requests whose HTTP response was lost. Select one to inspect its saved status. The response also offers View saved operation status. You can also type “Show laptop operation” followed by its 24-character reference, in Auto/Local mode. Status retrieval is read-only with respect to services, controller-only and independent of current local maintenance enablement. Historical audit-only references from before this change are not imported or fabricated.

States are running, complete, needs-attention, not-started and unknown. Permission revocation or cancellation before process dispatch records not-started. A persisted running record without a final receipt expires to unknown after the fixed operation timeout plus a one-minute margin when next inspected/claimed. The same request ID is never automatically dispatched again, including after expiry. A late result cannot overwrite an already unknown record. Check current services and private logs before explicitly making a new request; a new ID is a separate operation, and only the existing bounded launcher/check adapter is supported. This is not arbitrary-effect reconciliation.

Complete means the fixed child process returned successfully, not that every account/model/microphone is ready. Neither an HTTP timeout nor a restart is recorded as success. Audit text remains for local diagnostics; receipts contain no conversation text, child output or credentials. A final audit-file write failure can leave a valid final SQLite receipt even when the HTTP request reports an error; inspect the saved receipt rather than assuming failure or repeating the request.

Foundation schema 7 adds the receipt table and takes a pre-migration SQLite backup when upgrading an existing schema-6 database. Existing tasks, memory, coding evidence and permissions are preserved. Older application versions refuse the newer database rather than silently downgrading it. This is an initial durable invocation slice for two named operations, not a complete general Windows broker, scheduler, desktop helper or arbitrary-tool permission system.
