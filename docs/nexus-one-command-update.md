# One-command Windows updates

After the updater has been pulled once, run `Update-Nexus.cmd` on the laptop. It replaces the recurring manual sequence of git pull, process lookup, stop, dependency refresh, build and launcher restart. It uses the existing `feat/nexus-agent-router` branch and refuses to switch branches or discard tracked user edits.

The updater checks the current branch and tracked worktree, pulls with `--ff-only`, identifies only `node.exe` processes whose command line starts this repository's exact `node_modules/next/dist/bin/next start`, rechecks command line/creation time before stopping them, and waits for port 3000 to be free. An occupied/unrecognized service prevents the build. Ollama and the voice worker are not stopped by this process matcher.

A known generated `next-env.d.ts` difference between `.next/dev/types` and `.next/types` can be restored automatically only when the entire file otherwise matches HEAD, it is not staged, and there are no other tracked edits. Other local modifications stop the update. Untracked source files that conflict with git pull are left to git's normal refusal; there is no force/reset/clean step.

The first successful update, a changed package-lock hash or missing Next installation triggers `npm ci --ignore-scripts --no-audit --no-fund`. The locked application dependencies are installed; no model is acquired, global agent configuration modified or provider enabled. Then the normal production build runs, followed by the existing launcher. The success record is written only after the launcher exits successfully. Existing pairing, private workspace data, source selections and grants are retained.

A private `.gulf-wing/update.lock` prevents two updaters running concurrently. A leftover lock is not automatically reclaimed after an interruption. A failed pull stops before service shutdown. Dependency/build failure stops the sequence and may leave Mission Control stopped; it does not start a mismatched or partially rebuilt server. A failed optional service in the existing launcher may also prevent the final success record, even if Mission Control started. Inspect the visible command output and existing launcher logs before retrying. No automatic rollback or uncertain retry is claimed.

The native process query uses fixed PowerShell code with a task-specific environment regex; repository paths are data rather than interpolated PowerShell commands. npm invocations are fixed command strings with a controlled working directory. Node tests verify sequence, dirty/wrong-branch guards, failed pull/build and occupied-port behavior, process ownership matching and generated-file handling. The Windows-native updater has not been executed on the owner's laptop by cloud tests; it requires one local invocation because this cloud workspace has no laptop command channel.

After launch, the updater fetches the local public Nexus page and checks the bounded current CSS/JavaScript URLs under `/_next/static/` for successful responses and expected content types. It does not follow arbitrary external asset URLs. This catches the observed unstyled-page/static-asset failure before marking the update successful; HTTP readiness is not a substitute for the cloud's independent full browser tests.
