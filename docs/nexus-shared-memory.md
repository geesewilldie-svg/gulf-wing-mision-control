# Portable shared memory and Obsidian

## Video-driven second-brain contract

The owner's supplied transcript and screenshots are now mapped to concrete requirements in [Applied video and screenshot contract](nexus-second-brain-reference.md). Durable Markdown notes and a shared retrieval/write-receipt contract must carry relevant authorized work between permitted agents and future models. This is context reuse, not model training. The separate JARVIS video transcript is now supplied through 14:05; the hour-long Obsidian source remains excerpt-only. Source records preserve that distinction.

Existing snapshots and the completed-task journal are the first delivered slices. The next memory stages are a common adapter-facing retrieval envelope, authorized agent work-note receipts, stable current-note identity/revisions and explicit conflict/supersession/correction/forgetting semantics. Keep SQLite authoritative for owner facts/instructions, tasks, permissions and receipts; historical snapshots must not become current fact authority. A browse-only file does not become assistant memory simply because its star is visible.


The owner wants a lasting second brain shared across permitted agents and future models. Markdown knowledge should remain useful when a model changes; this supplies context rather than training a model. The animated Memory Galaxy is its visual entry point, with real file stars, zoom, nearby notes and explicit opening. Decorative stars do not represent invented memories.

## First delivered step

Foundation → Owner memory and instructions includes **Download [workspace] memory for Obsidian**. Choose the memory workspace and download a Markdown snapshot. Save it in a vault yourself if desired. The controller-authorized, same-origin export reads current database records at request time, includes up to 500 current records in that workspace, and records owner provenance, IDs, revisions and update/export times. Content is quoted; owner-stated facts are not independently verified. Tasks, model answers, conversation history and credentials are excluded. An empty workspace exports an explicitly empty note.

This creates a browser download, not an automatic write to a selected vault. Downloaded copies are private and do not synchronize: correcting or forgetting a record in Nexus does not erase exported copies, backups or copies already shared with another agent. The database remains authoritative for these records. No import or provider permission is granted.

## Next architectural stages

1. A dedicated Nexus-managed Markdown area in an explicitly configured Obsidian vault, with a clearly defined authority for each record. Preserve owner-created notes; track stable IDs, revisions and content hashes before any replacement. External edits must produce conflicts rather than silent overwrite.
2. Agent work notes with provenance: agent identity, source references, task/run IDs, timestamps, verification state and supersession. Separate owner statements, observations and unverified model proposals. Successful file writes do not verify claims.
3. Bounded automatic updates for authorized work, using durable write receipts, cancellation/revision checks and recovery after interruption. Define correction, forgetting and deletion propagation before enabling ongoing synchronization.
4. Relevant retrieval across allowed agents with workspace filtering, current access checks, context limits and existing per-provider sharing consent. Selecting a vault does not authorize external models to read it.
5. Galaxy views for these real notes alongside broader storage browsing. All-drive metadata browsing and original-file viewing remain separate adapters; the phone controls laptop-hosted sources without acquiring blanket phone-storage access.

The initial export did not enable automatic writes. The optional completed-task journal below is now the first bounded automatic note-writing capability; continuous synchronization, automatic fact learning from every conversation and general cross-agent delegation remain unbuilt.

## Reviewed vault snapshots

Run `Setup-Nexus-Memory-Vault.cmd` locally on Windows, select an already configured Obsidian vault, and confirm the displayed grant. Setup creates a new `Nexus Memory Snapshots` directory and a local `memory-vault.json` grant bound to that vault's ID and canonical path. Existing directories are not adopted. Repeating setup validates the same existing vault; it can locally re-enable a disabled grant, but does not switch an existing grant to a different vault. Setup sends no model request and saves no owner-memory note.

In Foundation, select the memory workspace and choose **Review [workspace] snapshot for vault**. Read the exact Markdown, then **Confirm and save new vault snapshot**. Confirmation regenerates the snapshot and checks its hash against the preview; changed memory or previews older than fifteen minutes require fresh review. Save creates a uniquely named batch directory and Markdown file, with byte/hash read-back before publishing the final `.md` name. It never replaces prior notes. The save now attempts to add only the new note to the selected-file index; open the galaxy or use Reload sources to see it, subject to normal file/index limits. Pending indexing is reported separately from the confirmed file save.

Saving requires controller authorization, same origin, explicit confirmation and local setup. Removing the selected vault or replacing the destination with a link/junction blocks saving. No arbitrary target paths or supplied Markdown are accepted by the endpoint. This is an owner-approved snapshot workflow, not continuous agent write-back. Old snapshots remain private copies: corrections/forgetting do not remove them. An uncertain/interrupted save must be inspected before retrying; a retry can create another snapshot. A crash may leave an unpublished `.tmp` file in its batch directory. Local users with permission to change grants or filesystem contents remain trusted; this is not an OS sandbox against a hostile local account.

## Reviewed task work notes

A task with a saved output in a settled state (completed, paused, waiting, failed or cancelled) offers **Review task work note for vault** on its Foundation card. The preview contains the task request, recorded status detail and complete stored output, with task ID, workspace, mode, revision, update/export times and artifact SHA-256. Text is quoted, and the document explicitly separates task history from owner-stated facts or instructions. The exporter does not establish a producing model identity; generated claims/code remain unverified, regardless of task completion. Active tasks and empty artifacts cannot be exported.

Confirmation reads the current task in its original workspace and regenerates the exact note. Changed output, revision or state invalidates its preview; deleted tasks are unavailable. The existing local vault grant, fifteen-minute preview limit and create-only file/read-back behavior apply. Each task note is retained independently; later task changes/deletion do not propagate to it. It can be browsed and read explicitly after index refresh. Retained Nexus snapshots are excluded from automatic answer context under the guard below. No new agent, inference, automatic write-back or owner-fact promotion is performed.

Vault save results and errors now appear beside their review controls. Changing workspace clears that control's preview/result; late responses from an earlier view are ignored. Each work-note control belongs to its task card. The native owner-memory vault snapshot was saved, reindexed and read successfully on Windows on November 23, 2026; the task-note workflow still requires native acceptance.

## Vault save status and revocation

Foundation's **Obsidian vault saves** panel checks local settings and the selected destination. It reports **Ready for reviewed saves**, **Vault saves disabled**, **Not set up**, or an unavailable/configuration state. Ready means the selected vault and dedicated folder passed metadata checks; it does not prove future write success, synchronization, indexing freshness or another agent's access. Only the selected vault label and fixed child-folder name are returned, never the absolute host path. Refresh status changes no settings and contacts no provider.

A paired controller can choose **Disable future vault saves**. This atomically records `enabled: false` in the existing local grant, retains its vault binding and leaves every snapshot/note intact. Disable also works when the selected drive is offline, provided the saved grant is readable. Saves validate the grant before creating a batch and again before publishing Markdown. A save already being dispatched may finish across the final filesystem boundary; disabling does not erase or retract it. Check the vault before retrying uncertain saves. Existing version-1 grants without an `enabled` field retain their prior enabled behavior.

Re-enable only through `Setup-Nexus-Memory-Vault.cmd` on the laptop: select the same vault and confirm. The existing vault/canonical folder is revalidated, including link/junction rejection. Browser status/disable operations cannot enable a grant, select a path or adopt an existing unrelated directory. Malformed settings are preserved for investigation. Manual saves remain reviewed and create-only. The automatic journal below requires a separate local opt-in; automatic fact learning and agent context-sharing grants are separate work.

## Current memory versus retained snapshot context

Retained Markdown copies must not silently override a corrected/forgotten database record or bypass local-only owner memory policy. The answer route therefore excludes recognized Nexus owner-memory snapshots and reviewed task work notes from **automatic document retrieval**, for knowledge-only search and every model choice. They remain in the source map/file galaxy and can still be searched/read through explicit laptop-file commands. Current owner records continue through the database's scoped, local-only context path; this change grants no external provider access.

Recognition uses the dedicated `Nexus Memory Snapshots` source path or the exported `# Nexus owner memory` / `# Nexus reviewed work note` heading. If any passage identifies a snapshot, all passages with that source label are withheld before ranking, including continuation chunks and renamed imports whose heading remains intact. The route shows a generic exclusion warning without exposing file names or content. Ordinary source documents are unaffected. This conservative policy supersedes the earlier assumption that retained work notes automatically join answer context after indexing. Revision-aware, workspace-scoped work-note retrieval is still future work.

This does not erase files or recognize arbitrary rewritten/partial copies that have lost both their source path and export heading. Explicit reads remain historical content, not current verified facts. Existing revision fences clear stale conversation after owner-memory changes; no universal deletion of every copied fact is claimed.

## Current local work context

Local model answers can retrieve relevant saved task artifacts directly from SQLite in the selected workspace. The lookup examines the latest 100 tasks with nonempty output in a settled state (completed, paused, waiting, failed or cancelled), uses lexical query matching, and supplies at most two records. Each record carries task ID, revision, state, workspace and update time, with bounded request/status text and a 600-character output excerpt. This is partial history, not a complete work ledger or semantic recall of every past interaction.

The prompt labels these records as untrusted artifacts, separate from owner facts/instructions. Task completion does not establish external execution, verification or model identity. The answer displays **Saved work used locally**, with `[W1]`/`[W2]` task references that can be reviewed in Foundation. These records are appended only to local prompts; external providers receive neither this task context nor recent conversation. Retained exported notes remain excluded from automatic document retrieval.

A workspace-specific work stamp hashes current task IDs/revisions/states/update times. The web client sends the last returned stamp with follow-up questions. Changed work resets conversation history; workspace switching resets the client history too. Local answers are discarded if the workspace's task stamp changes during generation, even if the changed task was not among the matching excerpts. This fences supported task mutations without changing worker policy or pausing other tasks. Clients that omit the optional stamp cannot rely on server detection of stale caller-supplied history. There is no retry, task execution, new fact creation or vault write in this retrieval path.

## Optional automatic completed-work journal

**Off by default.** After the reviewed vault destination is set up, run `Enable-Nexus-Work-Journal.cmd` on the Windows laptop. It displays the destination and asks for a separate local confirmation: automatically save new completed task artifacts from **all workspaces**, without reviewing each note. Repeating enable while already enabled preserves the original start time. Re-enabling after disable starts a new window; work completed while disabled is not automatically backfilled. Installing this update does not enable it.

While the laptop's Nexus server runs, a ten-second scheduler considers completed, nonempty task artifacts updated at or after the opt-in time. It does not start tasks, invoke models, infer facts, edit source notes or contact a provider. It reads the current task revision before dispatch and saves at most two artifacts per pass as new `# Nexus automatic work note` files in the existing snapshot area. Each records task identity/revision/state, timestamps, output hash and quoted text, and says it was not individually reviewed. This is a retained work journal rather than synchronized owner memory. Later task deletion/correction, grant disable or cancellation does not erase existing notes. A change after dispatch may leave a historical note; already-published files are not retracted.

Before destination writes, the scheduler exclusively claims the task ID/revision in `.gulf-wing/work-journal` and reserves one of 500 create-only capacity slots. Existing claims, including malformed, interrupted or unconfirmed claims, are never automatically replayed. A simulated/actual lost acknowledgement after publication may mean the note exists without a confirmed receipt; the owner must inspect it. Orphaned capacity reservations also count as uncertain and consume capacity. At the retained 500-attempt/reservation limit, publication stops; there is no automatic pruning, capacity reclamation or retry. Private temporary files can remain after interruption. The application assumes one trusted laptop installation; its private data directory is not a hostile-local-user sandbox.

Foundation shows whether the journal is enabled and receipt/uncertainty counts. **Disable automatic work journal** stops future automatic saves and leaves reviewed saves available. **Disable future vault saves** disables both. Grant checks before publication bound revocation, but a save already across the final filesystem boundary may finish. Only the local enable script can turn the journal on; no browser/model enable operation is provided. Status displays configuration and saved receipts, not proof of continuous scheduler health.

Newly written notes are incrementally added to an initialized selected-file index, without rescanning other selected folders. Open the galaxy or use Reload sources to see the updated map; index limits and deferred metadata handling are described below. Automatic notes, reviewed work notes and owner snapshots are excluded from both answer retrieval and planning evidence, including renamed imports retaining the export heading. Current local work context continues to come from SQLite. Agent/model identity attribution, verified observation capture, two-way vault edits, continuous cross-agent context sharing and owner-fact synchronization remain future work.

## Incremental note indexing

Confirmed reviewed saves and automatic journal saves attempt to add the exact new Markdown file to the current selected-file index. The writer supplies only its selected-root ID, relative snapshot name and read-back hash. The indexer restricts this operation to Nexus Markdown snapshots in a currently selected Obsidian root, verifies the file/hash and export heading, and preserves the other indexed entries. It does not open/reparse unrelated files, perform a full folder scan or replace source files. The full-scan timestamp remains unchanged; new file metadata records its own modification time. New additions are placed first so they can appear within the source map's existing 80-file display cap.

An initialized index matching the current folder selection is required. The normal 200-file, 8 MB file-size, 2-million-character and serialized-index bounds apply; a full/busy/unavailable/changed index or changed note leaves indexing **pending**, rather than reporting the confirmed file save as failed. Journal receipts separate `saved` from `indexing`, and Foundation reports pending indexing counts. At most two saved journal entries get metadata retries per pass, rotating fairly; retry never creates another Markdown copy. Publication claims with uncertain outcomes are not automatically indexed/replayed through this path. Disabling the journal stops its indexing retries too. Older receipts lacking relative-file metadata are not silently adopted.

Open/reload the galaxy or source map to fetch the updated index; an already open visual is not continuously pushed new nodes. Normal reads still revalidate selected files and withhold changed/unavailable versions. If the index has never been initialized or selection changed, use the existing full-refresh command once; limits or edited notes can also require manual index refresh. Shared in-process refresh fencing and a changed-base check protect index updates in this single-host application; this is not a distributed index transaction protocol. Snapshot exclusion from automatic answer and planning context remains in force.

## Journal history in Ask Nexus

Use **Show my work journal** for local configuration, receipt/reservation counts and up to ten recent entries across all workspaces. **Show my work journal issues** selects unconfirmed entries and notes with pending indexing; orphaned reservations may have no selectable entry. These whole-request commands require a paired controller and Auto/local mode. They read bounded saved receipts and settings, not models, provider quotas, task execution or source-note contents. Configuration/receipts do not prove scheduler health or a note's current availability.

Each entry distinguishes saved/read-back-at-the-recorded-time, skipped-before-write and unconfirmed outcomes, with recorded indexing status. New receipts include workspace; legacy records can lack it. A card may display the current database task label as a navigation aid, not a reconstruction of older note contents. **View journal entry** reads a specific task-ID/revision receipt; malformed or incomplete metadata stays unconfirmed, and no retry/recovery is performed. Raw paths, arbitrary error strings and malformed filenames are not returned. Valid saved filenames and hashes remain available in the receipt detail.

**Open indexed journal note** is a separate explicit file-read request using the saved root-relative reference's deterministic ID/hash. The existing selected-folder/current-version checks decide whether it can still be opened. A stale receipt cannot bypass changed folder permissions or file hashes. Older receipts without the file reference can still be inspected but do not gain an invented open action. History does not enable/disable the journal, write a note, refresh the index, claim that generated work is verified or promote it into owner facts.

See [the applied JARVIS capability plan](nexus-jarvis-capability-plan.md) for model switching over the same permitted memory service. Model identity, conversation context, voice/personality and tool permissions are independent state; changing one does not silently change the others.

The local answer route now consumes a versioned internal shared-memory context envelope with stable source revisions/hashes and separate owner/work provenance. All in-budget owner instructions remain intact; external audiences receive no private owner/work content. See `nexus-shared-memory-context.md`. This is an adapter-ready retrieval slice, not a newly connected provider or synchronized vault writer.

## Saved-note lifecycle tracking

The first version/identity catalog is now delivered for new reviewed snapshots and new automatic journal notes. Stable logical note groups and source-version/file hashes support read-only inspection of unchanged, externally edited, missing, unavailable and historical copies. Foundation's **Saved note versions** panel checks ten tracked files at a time. Existing files are never overwritten or imported, and registration failure remains separate from a confirmed save. Older unregistered exports are not automatically adopted. See `nexus-note-versions.md`; managed current-note replacement/conflict resolution and metadata recovery remain later stages.
