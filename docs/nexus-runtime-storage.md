# Runtime-reported Ollama storage and capacity

After an archive import review, **Inspect Ollama storage** explicitly requests additional local runtime/host observations. Regular review still performs only its previous runtime version request. The storage action repeats the source-bound archive review and does not import, create, generate, reserve disk or change a model selection.

The server uses only its own `OLLAMA_MODELS` setting, or its current user's `.ollama/models` default, as a candidate root. No caller path is accepted. From the bounded installed catalog it selects the first simple local name with a reported digest, calls fixed local `/api/show` with `verbose:false`, and accepts only one absolute `FROM` blob path matching that exact candidate's `blobs/sha256-<64 hex>` layout. Remote model declarations, foreign/relative/ambiguous paths and unavailable model evidence stay unknown. It does not enumerate drives, search other users' directories or scan other models/roots until something matches.

Before accepting an observation, all candidate-root/blob-directory ancestors must be ordinary directories, the reported blob must be an existing regular non-symlink file, and file/catalog/configuration identities must stay unchanged around inspection. Only file metadata is read; blob contents are not hashed. The helper checks filesystem capacity at both the store root and blobs directory and reports the minimum available bytes, covering differing mounts conservatively. Its free-space policy is two archive sizes plus 1 GiB of headroom. This is an observation, not a reservation, write-permission test or guarantee of adequate capacity for every runtime operation.

Runtime requests have a combined 15-second cooperative deadline, existing bounded catalog handling and a 500 KB show-response limit. Filesystem metadata operations themselves may not be immediately interruptible. Cancellation, unsafe identity, malformed/runtime failure or unsupported capacity stays unaccepted. Private paths, raw Modelfile/system text and arbitrary runtime metadata are withheld from the browser/export result. Known-field results retain model name, candidate-source category, observation time, capacity and bounds only.

`runtimeStorage.state: observed` means reported path agreement and host metadata/capacity were observed. `runtimeStorageVerified` remains false: runtime process identity, blob contents, future destination binding and actual import writes are not independently verified. The write adapter must revalidate its destination and capacity when implemented. Native Windows paths/junctions, differing service environments, custom/cloud/container stores and empty catalogs may remain unknown instead of being inferred compatible.

Tests use disposable local stores and synthetic runtime responses; the compiled production API is also exercised with an owned loopback runtime and empty catalog. No real model import, generation or native Windows destination acceptance is inferred.
