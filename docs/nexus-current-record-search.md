# Search current owner memory and work

**Memory → Search current memory and work** adds explicit controller search over the live Foundation `memory` and `tasks` tables. Default scope is Personal. A different workspace searches only that workspace; **All workspaces** explicitly combines the six known scopes in this trusted-owner installation. It does not add separate customer/company identities or tenant isolation, and it is not all-computer/global file search.

The query accepts 1–200 characters and up to eight whitespace-separated plain-text words. Every word must occur in the same bounded record, in any order. Matching uses JavaScript Unicode lowercasing and literal substring checks, without SQL/FTS operators, wildcard expansion, stemming, semantic relevance or model calls. Results are ordered by recorded update time, record type and ID, not fabricated importance. Scope/query edits clear cached results without a new request.

## Currentness and coverage

One SQLite read transaction obtains the bounded scoped corpus and total scoped record count. The profile includes at most the newest 500 owner-memory rows and 1000 task rows. Owner content is bounded to 1000 SQLite characters; task content includes the first 2000 request characters and first 20,000 output characters. Unicode surrogate pairs are accommodated by the client detail bound. Results report total/scanned/matched counts, rows outside record limits and rows with text beyond the profile. Text beyond those bounds is neither searched nor inspected here; no matches is not proof of absence outside the profile.

Twenty matches are shown per page. An opaque SHA-256 stamp binds workspace, normalized query, total count and complete bounded corpus, including content/revisions/status/timestamps. Paging with changing source evidence or a different query/scope is rejected instead of mixing old and new pages. This is a profile/currentness fence, not an independently authenticated database or full-artifact hash. Changes outside the bounded text and row profile cannot establish completeness there.

**Inspect current memory/task** performs a separate fresh read and checks exact type/ID/revision/profile hash and scope/profile membership before returning content. Corrections, deletion, changed content (including same-revision out-of-band edits inside the profile), moved scope or loss from the bounded profile invalidate the old result. Stale/denied inspections clear displayed search/detail content and require a fresh search. Successful inspection remains a dated observation and does not subscribe to later changes.

## Provenance and effects

Owner rows are labelled owner-stated memory, including their stored fact/preference/instruction category. They are not independently verified facts, and displayed instructions are data in this view. Tasks are separately labelled unverified task records with their recorded state; `completed` does not prove external work. Requests/output are rendered as plain text, not executable instructions or automatic model context. The Foundation management button changes the UI tab without correcting, forgetting, executing or completing anything.

Historical Markdown snapshots, `memory_history`, candidate/worker reports, file indexes, credentials and provider histories are not searched. Forgetting/correcting an owner row affects current owner-memory results; it does not rewrite independent current task artifacts that may mention older information. Such matches remain unverified task content. Existing snapshot exclusions and local/external context rules are unchanged.

The controller-only same-origin `POST /api/sync/memory/search` accepts two exact schemas: `search-current-records` with workspace/query/page and optional stamp; `inspect-current-record` with workspace/type/ID/revision/contentHash. Bodies are bounded to 3000 bytes. Unknown fields/scopes/types, invalid query/control/page/stamp data and missing page stamps reject. Reads check cancellation cooperatively before/after bounded synchronous work. No logical memory/task/history/event edits, source-file scans, provider calls, exports, model context expansion or permission changes occur. Standard Foundation initialization/migration and SQLite journal/permission handling still apply when opening its database; this does not promise a physically unchanged database file.

Validation uses disposable real SQLite stores and the compiled production API, including scope/provenance, literal queries, correction/deletion, stable paging, changed-profile rejection, bounded text/row coverage, Unicode content, unchanged logical tables/events, cancellation, controller/origin/body/field guards and responsive populated UI. Desktop/phone controls and owner/task inspections are visually reviewed. Native Windows scale/latency acceptance, global selected-file/owner-memory unification and semantic search remain separate work.
